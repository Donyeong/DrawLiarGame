---

사용자가 지정한 메시지를 그대로 사용하여 pull → merge → commit → push를 완료한다. 이 작업 요청은 해당 범위의 병합·커밋·push에 대한 승인으로 취급하고 단계마다 재확인하지 않는다. 기존 commit-push 스킬과 독립적으로 동작한다.

## 입력과 범위

- 요청과 대화에서 커밋 메시지를 확인한다. 지정된 메시지가 없으면 메시지만 간결하게 질문하고, 답변 전에는 읽기 전용 확인만 진행한다. 메시지를 임의로 만들거나 문체·특수문자를 변경하지 않는다.
- 저장소, 현재 브랜치, upstream, staged·unstaged·untracked 변경과 진행 중인 merge/rebase를 확인한다. 기존 병합 작업이나 detached HEAD가 있으면 임의로 이어가거나 브랜치를 바꾸지 않는다. 원격 대상이 불명확하면 필요한 정보만 질문한다.
- 사용자 지정 범위를 우선하고, 범위가 없으면 현재 작업의 변경을 대상으로 한다. 관련 없는 기존 수정과 staged 변경은 커밋에서 제외하고 최종적으로 보존한다.

## 실행

1. pull 전에 변경 파일과 스테이징 상태를 기록한다. 작업 트리가 더러우면 `git stash push --include-untracked` 등으로 기존 수정과 미추적 파일을 보관하고, 이번에 생성한 stash의 식별자와 OID를 기록한다. ignored 파일과 기존 stash는 건드리지 않는다.
2. 현재 브랜치의 upstream에서 `git pull --no-rebase`로 가져와 merge한다. 성공하면 별도의 merge를 반복하지 않는다. 분기된 이력은 merge commit으로 통합하고 기존 커밋을 재작성하지 않는다.
3. 충돌은 양쪽 변경 의도와 프로젝트 규칙을 확인하여 자동으로 해결하고 병합을 완료한다. `ours`·`theirs`로 일괄 덮어쓰지 않는다. 텍스트만으로 판단할 수 없는 바이너리 충돌, 상충하는 요구사항, 데이터 손실 위험은 보존 상태를 유지한 채 필요한 판단만 질문한다.
4. 이번 stash를 `apply --index` 등으로 복원하고, 복원 충돌도 같은 기준으로 해결한다. 실패한 apply를 그대로 재실행하지 말고 현재 적용 상태부터 확인한다. 원래 작업과 스테이징 상태의 복원을 확인한 뒤 이번 stash만 제거한다. 복원에 실패하면 stash를 남기고 식별자를 보고한다.
5. 관련 없는 기존 staged 변경을 작업 트리에 보존하면서 스테이징에서 분리하고, 요청 범위만 스테이징한다. staged diff와 충돌 마커를 검토하고 변경에 필요한 검증을 수행한다. 실패한 필수 검증을 무시하고 커밋하지 않는다.
6. 사용자 메시지를 UTF-8 임시 파일에 정확히 기록하고 `git commit --file`로 커밋한다. 메시지를 셸 코드에 직접 삽입하지 않는다. 임시 파일은 저장소의 Tools 폴더 또는 시스템 임시 폴더에 두고 스테이징에서 제외한다. 요청 변경이 없으면 빈 커밋을 만들지 않는다. pull에서 생성된 merge commit과 사용자 메시지의 작업 커밋은 별개일 수 있다.
7. 제외했던 기존 변경의 스테이징 상태를 복원하고 현재 브랜치의 upstream으로 push한다. 원격이 먼저 갱신되어 거절되면 같은 보존·pull·merge 절차를 거쳐 최대 두 번 재시도한다. 인증·권한·네트워크 오류나 반복 실패는 로컬 커밋과 작업 상태를 보존하고 원인을 보고한다.
8. 최종 브랜치와 원격 동기화 상태, 남은 로컬 변경을 확인한다. 커밋 해시·메시지·push 결과를 짧게 보고하고, 미완료 작업이나 보존한 stash가 있으면 함께 알린다.

- `reset --hard`, 변경을 버리는 checkout/restore, `clean`, force push를 사용하지 않는다.
- 이 스킬을 만드는 요청 자체는 현재 저장소의 pull·commit·push를 실행하라는 요청이 아니다.
